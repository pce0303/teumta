## 📱 프론트 담당 — 지금 최우선

**목표: 검색 → 혼잡 확인 → 우회 코스 → 진행 흐름을 앱에서 끝까지 동작시키기.**

### 서버가 이미 주는데 아직 안 쓰는 것 3개

1. **TOUR 목적지도 실시간 혼잡도 조회 가능** — 상세 화면에서 `source === 'TOUR'`일 때
   "미제공"으로 두던 자리에 `GET /api/congestion?contentId=<tourApiContentId>` 를 붙인다.
   경복궁 같은 주요 관광지에서 실시간 혼잡도가 뜬다(서버가 TMAP POI를 매칭해 준다).
2. **`404 CONGESTION_DATA_NOT_FOUND`** — 실시간 혼잡도 미제공 장소는 이제 502가 아니라 404로 온다.
   "이 장소는 실시간 혼잡도를 제공하지 않아요" 안내로 처리(기존 `unavailable` 문구 재사용).
3. **집중률 예측** — 검색 응답의 `placeId`가 `null`이 아니면
   `GET /api/places/:placeId/concentration-forecast` 로 30일 날짜별 집중률을 보여줄 수 있다.

### 코스·진행 흐름 (코스 데이터가 들어가면 바로 가능)

4. 코스 목록/상세 — `GET /api/places/:placeId/routes`, `GET /api/routes/:routeId`
   (`stops[].pathFromPrevious` 폴리라인으로 지도 경로. 복귀 구간은 `Route.returnPath`)
5. 코스 진행 — `POST /api/trips` 로 시작, 진행 상태는 단말 local state
6. TripEvent 전송 — `POST /api/trips/:tripId/events`
   - ⚠️ **서버가 허용하는 이벤트는 `TRIP_STARTED`/`TRIP_COMPLETED`/`TRIP_CANCELLED` 3종뿐**이다.
     `PLACE_ARRIVED`·`MAIN_PLACE_RETURNED`은 현재 400 — 성과 분석 지표와 함께 확장 여부 결정 필요(아래 참조)

### 남은 수정

7. **출처 표기 범위** — `TourApiAttribution`이 상세에서 `source === 'TOUR'`일 때만 붙는데,
   **TMAP 상세의 "근처에서 잠깐 둘러볼 곳" 목록도 TourAPI 데이터**다. 주변 장소 목록이 보이면
   source와 무관하게 표기해야 한다(요강상 출처 표기는 필수)
8. 앱 안에서 "한국관광공사"·"KTO"를 **출처 표기 외 용도로 쓰지 않는다**(요강 규정)
9. 우회 제안 강조 기준 — `CROWDED` 이상에서 우회 코스 진입을 강조
   ([congestion-rules §5](./congestion-rules.md) 확정 기준)

### 상시 원칙

사용자 GPS를 서버로 보내지 않는다(서버 API에 좌표 파라미터 자체가 없음).
검색 자동완성 금지(버튼 또는 500ms+ debounce) — 외부 API 쿼터.

### 남은 것

1. **분산 효과 지표 정의** — 성과 분석 화면에 넣을 지표의 분모/분자를 확정한다.
   ⚠️ **현재 서버는 Trip 단위 이벤트 3종만 기록한다**(시작/완료/취소). 즉 지금 계산 가능한 것은
   우회 선택률·완료율뿐이고, **로컬 도착률·복귀율은 계산할 수 없다.**
   - 필요하다면 `PLACE_ARRIVED`/`MAIN_PLACE_RETURNED` 허용을 요청할 것(privacy 제약상 좌표 없이
     eventType + placeId만 기록하면 원칙 위반은 아니다 — location-privacy.md 확인)
   - 필요 없다면 "측정 계획"으로 발표에 넣고 구현은 생략
2. **공모전 스토리** — "관광객을 줄이지 않고 발걸음과 지갑을 옆 골목으로 옮긴다" 프레임으로
   기능설명서 골격. 해시태그별 기능 흐름도가 제출 필수 항목이다
3. **위치정보 아키텍처를 강점으로 서술** — 단말 내부 처리 + 서버 미전송 구조가 요강 FAQ의
   위치기반서비스사업자 **비신고 요건에 그대로 부합**한다. 확정하려면 위치정보지원센터(lbsc.kr)
